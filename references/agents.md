# Worker coordination

Use Sonnet 5.5 or Sol 6.1 for the coordinator and Haiku or Luna for case workers when the host provides them. Read the host's available worker capacity and use up to five active case slots.

## Coordinator

Use the host's own agent mechanism (Claude Code's Agent tool, Copilot CLI agents, ...) for the case workers; oqa spawns no CLI or model of its own. `oqa dispatch --plan [--limit N]` claims the free cases (at most five) and prints one brief per case: give each brief, as it is, to one agent. When an agent reports it is done, run `oqa dispatch --settle CASE`: it replays the saved script and checks the conclusion against the facts (fixtures not unique to this run, a conclusion that blames leftover data), reopening the case once for a new agent when it finds a cause. A PASS whose script does not replay is NOT reopened: its live result and pictures are final. `oqa dispatch --repair CASE` prints a brief for one agent that fixes only the script (`oqa live script`, then `oqa live replay`, at most three tries; about 30 seconds a try, against minutes for a new live run); run `--settle CASE` again afterwards, and only when the script cannot be fixed use `--settle CASE --reopen`. Which cases run is the user's choice: the dashboard lists every ready case with a tick (all ticked by default) before the strategy is approved, and the cases left out can be added later, in the same session, from the dashboard or with `oqa run-more` (the user's own action: it needs a real terminal). In Claude Code, start one sub-agent per brief with the Agent tool, all in the same message so they run in parallel: `prompt` = the brief as printed (it is built from the live session: the case's plan, the user's answers and hints, earlier conclusions, shared notes and recent events, so a retry already knows what went wrong), `subagent_type` general-purpose, `model` chosen per case (haiku for a simple case, sonnet for a case that needs prepared data, an import or several profiles). No agent definition file is needed: the agents exist for this run only. When workspace knowledge holds business facts (rule, quirk, error, fix, data, locator) and some free case has had none chosen, `--plan` hands out no worker: it prints ONE brief for a cheap agent (haiku) that names, by meaning, the facts each case needs. The agent writes the JSON and runs `oqa knowledge pick --file`; run `--plan` again and the chosen facts lead each case packet and brief (`--skip-knowledge` bypasses). Run `--plan` again until no case is free and none waits for a result. oqa never starts a model itself: a host that cannot start sub-agents cannot run cases in parallel, it works through the briefs one at a time. What the user presses on the dashboard (dispatch or hand over a case, generic script) is only a request: `oqa wait` tells the coordinator, who gives the brief to a sub-agent of the host. Generic script: `oqa live regenerate CASE|all --brief` prints one brief per case; the sub-agent writes the script to the file named in the brief and runs `oqa live regenerate CASE --candidate FILE` (static checks, two fresh replays), which answers PASS, RETRY with the reason (the original script stays in place, at most three submissions) or FAIL; `--cancel` closes a rewrite nobody finishes. `oqa tool CASE NAME --args JSON` gives a worker the tools that have no `oqa live` command (`--list` shows them).

- After approval, read `oqa status` and `oqa claims`. Assign ready cases to separate workers. Pass the session ID, workspace and case ID.
- Workers use `oqa claim --agent WORKER --case CASE --packet` to get ownership and the case context together. A dependent case waits for its prerequisites. If a prerequisite fails, record the reason the dependent case cannot run.
- Ask the data agent to check `oqa fixture plan SCREEN` when a case needs setup. Keep requested records, fields and returned identifiers in case-scoped `oqa note` messages. Visual-only cases can inspect the UI directly.
- When a worker stalls, get `oqa case context CASE --screen SCREEN --issue ERROR`. Share relevant sitemap, history and knowledge. Retry a runner failure only after identifying a concrete change. A confirmed mismatch is a test result.
- To look up one missing route or validation, use `oqa case context CASE --only sitemap|knowledge --screen SCREEN --issue TEXT`, or worker MCP `context` with the same fields. Apply knowledge only within its business condition, profile and state. Verify the current behavior on the live UI.

- Read worker `diagnosis` notes before deciding anything. Help with a concrete change (another locator, data, a document) and let the worker continue. A worker that stopped or is too slow is handed over with `oqa live handover CASE --reason ... [--to WORKER]`: its open attempt, recorded steps and attempt count stay, so nothing is redone and no recovery budget is used. `oqa live recover` is for an attempt that must be thrown away; it uses the one recovery.
- A conclusion you reopen is kept in the case history with what replaced it. Classify every non-PASS: application defect (FAIL, with evidence), automation issue or missing precondition (BLOCKED/PENDING, with the diagnosis).
- Replay results are separate (Replay PASS/FAIL/NOT RUN): after a run use `oqa live replay all --fast --headless` and treat a Replay FAIL as a script problem to fix, never by weakening an assertion.

## Case worker

1. Claim the case and read `oqa case context CASE`. Use the session and workspace flags on every command. Pass the worker ID from the brief with `--agent` on live case commands. Start with `oqa live start CASE` and use the browser name returned by that command.
2. Inspect the real page before choosing actions. Prepare a case-owned record for state changes, edits or deletes. Run `oqa fixture ui SCREEN --case CASE --key FIELD --values FILE` with a JSON object of field values and a workspace-prefixed unique key. The tool records the setup for the next step. A relation can refer to an earlier fixture with `{"$fixture":"PREFIX_name"}`.
3. Follow [evidence requirements](evidence.md) and each step's `evidence` plan. Capture every meaningful UI action and intermediate state, including opened forms, entered values, controls before clicking and results after clicking. Use `live shot --caption TEXT` (MCP `evidence_before`) for supporting captures and `live step` to record the observed result. For a database step, run `oqa pgadmin shot CASE --n N --sql "SELECT ..."` (MCP `pgadmin_shot`) immediately after the affected record is saved. Query this run's fixture and select the named fields in the approved `database` rows. Record its PASS or FAIL with `live step`, including the observed Odoo state in `--actual`. Correct an UNVERIFIED query or diagnose the blocker. Write observations and analysis in Vietnamese and use the case context's `evidence_language` for supporting picture captions. Inspect the pictures and frame the exact unique target. Follow the [replay instructions](replay.md) for saved actions and visible Odoo checks. The live run performs database checks. Use run variables for record IDs, keep secrets out of saved code, and wait for observable states.
4. Verify before concluding. Operate the right control: a link inside a cell is not the empty area of the cell; confirm in the snapshot which element you used. Compare messages by text in the UI language against the documented message (`message_codes` in the case context); a code such as ERR_015 is not UI text. After Save or Discard wait for the state you check (onchange included) and assert the specific value, not a label that is always on the page. The picture must show that value and the target.
5. When stuck, do not close the case because a selector was not found or time passed: `oqa live diagnose CASE --category automation --detail "what you saw" --tried "locators and results"` (or `--category precondition --need "..."`), try what the coordinator answers, and only then close BLOCKED/PENDING with `--category`. A FAIL names the verified control: `--control`.
6. Create records through the screen: `oqa fixture key`, `oqa fixture ui ledger|license_user|contract ...`; use existing records only as `{"$ref": ...}` (read only). Relative dates use `{"$date": N}`. Never write through the ORM or edit the DOM to produce a UI outcome.
   Use short business labels for each fixture key, for example `--label "mặt hàng đối chứng"`. The tool combines the business name, case and run identity into a unique `AUTO_TEST_` key.
7. Close with `oqa live end CASE --status STATUS`. Report the result, reason and any remaining fixture data. The coordinator generates the workbook after the queue drains.


## Knowledge summary (after the last case)

The summary is written from what the run recorded: `oqa note` messages, diagnoses, hints, repairs and non-PASS reasons. A worker that tells the coordinator a lesson only in its final reply loses it: workers share lessons with `oqa note --case CASE` before `oqa live end` (the brief says so), and the coordinator notes any lesson that is only in a final reply before `oqa report`.

`oqa report` writes the workbook but keeps the session in REPORT while a knowledge summary is owed (the run left notes, diagnoses, hints, repairs or a non-PASS case). `oqa knowledge digest` prints a brief for ONE cheap agent (haiku); the agent writes a JSON array of lessons (screen, kind, fact, condition, evidence, ref, scope workspace|shared) and runs `oqa knowledge draft --file`. The user edits, drops, chooses the scope of each item and saves or skips on the dashboard (`oqa wait` reports it); then `oqa report` again closes the session. `oqa knowledge status` says what is owed.
